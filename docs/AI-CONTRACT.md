# AI-контракт

## Назначение

AI-компонент помогает бизнесу уточнить короткое описание задачи перед созданием карточки.

Он используется только для формирования уточняющих вопросов.

AI не:

- назначает команды;
- выбирает исполнителей;
- ограничивает доступ студентов к задачам;
- принимает решения вместо бизнеса;
- добавляет неизвестные факты в карточку.

---

# Статус реализации

В текущем MVP используется **локальная детерминированная AI-заглушка**.

Это не вызов внешней языковой модели.

Заглушка:

1. получает черновик задачи;
2. получает направление задачи;
3. анализирует уже заполненные поля;
4. определяет недостающие сведения;
5. формирует релевантные уточняющие вопросы;
6. возвращает данные в фиксированном JSON-формате.

Исходный контекст сохраняется без изменения.

Остальные сведения заполняет пользователь.

Пользователь может отредактировать любые данные перед подтверждением карточки.

---

# Вход

AI-функция принимает JSON:

```json
{
  "draft": "Короткое описание задачи",
  "topic": "Направление",
  "fields": {
    "title": "",
    "context": "",
    "need": "",
    "users": "",
    "data": "",
    "constraints": "",
    "result": "",
    "criteria": "",
    "contact": "",
    "interaction": ""
  }
}
```

## Поля

### `draft`

Исходное описание проблемы, введённое бизнесом.

### `topic`

Направление задачи.

Например:

```text
Ритейл
Образование
Финансы
Логистика
```

### `fields`

Текущее состояние карточки.

AI не должен добавлять в эти поля сведения, которых пользователь не предоставил.

---

# Промпт-контракт

```text
Ты помогаешь бизнесу уточнить задачу для студентов.

Вход:
JSON {draft, topic, fields}.

Правила:

- используй только факты пользователя;
- не заполняй пропуски догадками;
- верни JSON {mode, questions, fields};
- задай не менее 3 уместных вопросов;
- вопросы должны относиться к пропущенным или неясным сведениям;
- fields должен содержать только данные пользователя;
- пользователь редактирует и подтверждает карточку;
- не выбирай и не назначай команды.
```

---

# Формат ответа

```json
{
  "mode": "local-stub",
  "questions": [
    {
      "field": "data",
      "question": "Какие данные или материалы вы можете предоставить?"
    }
  ],
  "fields": {}
}
```

## `mode`

Для текущей реализации:

```text
local-stub
```

Это явно показывает, что внешняя языковая модель не используется.

## `questions`

Массив уточняющих вопросов.

Каждый вопрос содержит:

```json
{
  "field": "имя_поля",
  "question": "текст вопроса"
}
```

Допустимые поля:

```text
context
need
users
data
constraints
result
criteria
contact
interaction
```

AI должен вернуть не менее трёх вопросов.

## `fields`

Содержит только сведения пользователя.

AI не должен самостоятельно заполнять неизвестные значения.

---

# Пример входа

```json
{
  "draft": "У кофейни остаётся выпечка. Хотим точнее планировать закупки.",
  "topic": "Ритейл",
  "fields": {}
}
```

---

# Пример ответа

```json
{
  "mode": "local-stub",
  "questions": [
    {
      "field": "users",
      "question": "Кто будет пользоваться решением и какую задачу эти люди решают?"
    },
    {
      "field": "data",
      "question": "Есть ли история продаж, остатков или обращений? В каком формате и за какой период?"
    },
    {
      "field": "criteria",
      "question": "По каким измеримым показателям вы примете результат?"
    }
  ],
  "fields": {
    "title": "",
    "context": "У кофейни остаётся выпечка. Хотим точнее планировать закупки.",
    "need": "",
    "users": "",
    "data": "",
    "constraints": "",
    "result": "",
    "criteria": "",
    "contact": "",
    "interaction": ""
  }
}
```

Это сокращённый пример.

Текущая локальная реализация может формировать дополнительные вопросы по другим незаполненным полям.

---

# Тематические вопросы

Заглушка может использовать более подходящую формулировку в зависимости от направления задачи.

Например, для направления:

```text
Ритейл
```

вместо общего вопроса о данных может использоваться:

```text
Есть ли история продаж, остатков или обращений?
В каком формате и за какой период?
```

При этом AI по-прежнему не добавляет самих данных в карточку.

---

# Проверка ответа

Перед использованием результат проходит через:

```text
validate_ai_result
```

Проверяется:

- ответ является объектом;
- присутствует массив `questions`;
- имеется не менее 3 вопросов;
- используются только допустимые имена полей;
- текст вопроса не пустой;
- вопрос имеет допустимую длину;
- `fields` имеют ожидаемую структуру;
- исходные пользовательские данные не были изменены;
- AI не добавил новые факты.

При нарушении контракта результат не принимается.

---

# Обработка ошибки

Если AI-результат не проходит валидацию:

1. сервер возвращает JSON с ошибкой;
2. интерфейс показывает сообщение пользователю;
3. введённый черновик не теряется;
4. пользователь может повторить действие.

Основной сценарий приложения не зависит от внешнего AI API.

---

# Связь AI и рейтинга

AI **не рассчитывает рейтинг напрямую**.

Последовательность разделена:

```text
AI
↓
уточняющие вопросы
↓
ответы пользователя
↓
редактируемая карточка
↓
подтверждение бизнеса
↓
расчёт рейтинга
```

Рейтинг рассчитывается отдельной серверной логикой.

Это позволяет:

- не доверять AI итоговое решение;
- сохранять прозрачную формулу;
- показывать пользователю, за какие сведения начислены баллы.

---

# Human-in-the-loop

Финальное решение всегда остаётся за человеком.

Перед публикацией бизнес:

1. просматривает сведения;
2. при необходимости редактирует их;
3. подтверждает карточку;
4. только после этого публикует задачу.

AI-ответ не считается подтверждённым автоматически.

---

# Подключение внешней модели

В следующей версии локальное формирование вопросов можно заменить вызовом LLM на сервере.

При этом необходимо сохранить тот же контракт:

```text
{draft, topic, fields}
        ↓
AI
        ↓
{mode, questions, fields}
```

Необходимо:

- хранить API-ключ только в переменной окружения;
- установить timeout;
- ограничить размер ответа;
- требовать структурированный JSON;
- проверять результат через `validate_ai_result`;
- не принимать новые факты без подтверждения пользователя;
- иметь fallback на локальный режим при недоступности API.

---

# Fallback

Если внешний AI недоступен, приложение может переключиться на:

```text
local-stub
```

При этом продолжают работать:

- создание задач;
- редактирование карточки;
- рейтинг;
- публикация;
- каталог;
- отклики;
- ручное решение бизнеса.

Таким образом, AI улучшает процесс уточнения, но не является единственной точкой отказа системы.

---

# Будущее расширение

В текущем MVP AI не извлекает новые структурированные факты из свободного текста, кроме сохранения исходного контекста.

Для более сложного варианта можно добавить отдельный контракт:

```text
извлечённое значение
+
цитата-основание из текста пользователя
+
подтверждение человеком
```

Только после подтверждения такое значение может попасть в карточку.

Это расширение не входит в текущий MVP.

---

# Ключевой принцип

AI используется как помощник для уточнения задачи.

Он:

> спрашивает, но не решает за пользователя.

Бизнес подтверждает данные.

Рейтинг считается прозрачной отдельной логикой.

Студенты самостоятельно выбирают задачи.

Бизнес самостоятельно выбирает команды.
